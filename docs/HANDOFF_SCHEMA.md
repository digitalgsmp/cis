# CIS Handoff Schema and Separation Law
# Status: OPERATIONAL
# Updated: 2026-04-30
# Canonical path: /mnt/projects/cis/docs/HANDOFF_SCHEMA.md

---

## Purpose

Define what belongs in each institutional continuity artifact so that
no layer duplicates, overwrites, or silently absorbs another.
Separation is constitutional. Blurring layers creates drift.

---

## Artifact Responsibilities

### Project Primer (00–11 + 2_CIS_REORIENTATION.md)
Purpose: Long-term institutional orientation for any AI model starting a session.
Contains:
  - Named architectural problems
  - Constitutional governing principles
  - Layer stack and system map
  - ADR summary and status
  - Operational reality (what works right now)
  - Known risks
  - Open questions
  - Active and transitional components
  - Foundational contract distinctions
  - Long-arc sequencing

Does NOT contain:
  - Session-specific operational state
  - What was built in the last session
  - Immediate next-step task lists
  - Unresolved session-level conflicts (those go to Conflict Register)

Update frequency: End of any session that introduces new architectural concepts,
named problems, layer changes, or constitutional decisions.

---

### Session Handoff (CIS_Handoff_TIMESTAMP.md)
Purpose: State transfer between active sessions.
The handoff is not a second primer. It is operational-state continuity.

Contains:
  Field 1 — Session Focus: one sentence
  Field 2 — Completed: past-tense list of what was built/fixed/decided
  Field 3 — Next Steps: prioritized immediate actions
  Field 4 — Notes: warnings, deferred context, partially built work
  Field 5 — Verification Status: manifests, verification runs, unresolved FAILs

  Architectural State:
    Important non-implemented realizations from this session that materially
    affect future decisions. Concise. Current. Not historical essays.

  Active Transitional Implementations:
    Temporary operational patterns active this session that must not be
    mistaken for final architecture. Reference 11_TRANSITIONAL_IMPLEMENTATIONS.md
    for the full list; add session-specific items here.

  Conflict Register Updates:
    Conflicts added, resolved, deferred, or superseded this session.
    Each entry: title, status change, brief note.

  Intake / Draft Layer Status:
    Current ADR-048 maturity. What intake automation exists or doesn't.
    What the human is still doing manually that ADR-048 will eventually replace.

Does NOT contain:
  - Full primer content (that lives in the primer)
  - Historical architectural reasoning (that lives in distillations)
  - Detailed contract text (that lives in contracts)
  - Long-form governance definitions

Update frequency: Every session close. Generated by session.py.

---

### Session Distillations (SESSION_DISTILLATIONS/YYYY-MM-DD_topic.md)
Purpose: Compressed insight artifact. Permanent historical record of what
was decided and why, without raw transcript noise.

Contains:
  - Session Focus
  - Key Decisions
  - Architectural Insights
  - Operational Changes
  - Risks Identified
  - Deferred Work
  - Next Actions

Does NOT contain:
  - Conversational filler
  - Model personality
  - Repeated reasoning
  - Speculative implementation claims
  - Raw transcript excerpts

Update frequency: One per significant session. Written at session close.

---

### Conflict Register (CIS_CONFLICT_REGISTER.md)
Purpose: Track discovered contradictions, naming collisions, stale claims,
unsafe drift, and deferred structural bugs before they disappear into
chat history.

Contains:
  - Title
  - Status (OPEN / DEFERRED / RESOLVED / SUPERSEDED)
  - Severity
  - Category
  - Conflict description
  - Risk if unresolved
  - Observed during
  - Immediate action
  - Required resolution

Does NOT contain:
  - Resolved items that have been fully cleaned (move to RESOLVED status, keep entry)
  - Speculative future risks (those go to 07_KNOWN_RISKS.md)

Update frequency: Any time a conflict is discovered. Must be updated before session close.
Tool: cis_conflict_append.py

---

### Dashboard Session Close (POST /api/session/close)
Purpose: Structured operational record only. Triggers file writes and DB logging.

Contains:
  - The five session close fields
  - Four architectural state fields (new)
  - Verification status

Does NOT contain:
  - Primer content
  - Contract text
  - Historical reasoning

## What Belongs Where — Decision Table

| Content Type | Primer | Handoff | Distillation | Conflict Register |
|---|---|---|---|---|
| Named architectural problem | ✓ | Brief ref | ✓ | If unresolved |
| Constitutional principle | ✓ | — | ✓ if new | — |
| What was built this session | — | ✓ | ✓ | — |
| Immediate next steps | — | ✓ | ✓ | — |
| Known risk | ✓ | If new/active | — | If structural |
| Open question | ✓ | — | — | If urgent |
| Discovered contradiction | — | ✓ note | — | ✓ always |
| Transitional implementation | ✓ | ✓ if active | — | If dangerous |
| ADR status | ✓ | If changed | ✓ if locked | — |
| Verification results | — | ✓ Field 5 | — | If FAILs |
| Intake layer status | ✓ | ✓ | ✓ if changed | If gap is risk |

## Separation Rules (Constitutional)

1. The handoff is not a second primer.
   Primer = institutional continuity. Handoff = session continuity.

2. The conflict register is not a task list.
   It tracks structural problems, not implementation TODOs.

3. Distillations are permanent compressed artifacts.
   Do not retroactively edit them. Write a new one if corrections are needed.

4. The dashboard session close is operational only.
   It triggers writes. It is not a governance document.

5. Any concept introduced in a session that affects future architectural
   reasoning must reach the primer before that session closes.
   Handoff alone is insufficient for architectural continuity.

## Primer Update Trigger Criteria

A primer update pass is required when a session introduces:
  - A new named architectural problem
  - A new layer or system concept
  - A new ADR (locked or pre-draft)
  - A change to constitutional governing principles
  - A change to operational reality (something new works or stops working)
  - A new risk category
  - Resolution of a previously open question
  - A filesystem taxonomy or governance decision

A primer update pass is NOT required for:
  - Routine build work within an existing ADR
  - Bug fixes with no architectural implications
  - Minor configuration changes
  - UI adjustments within existing constraints
