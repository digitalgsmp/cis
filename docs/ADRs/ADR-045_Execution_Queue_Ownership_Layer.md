# ADR-045 — Execution Queue Ownership Layer
# Status: LOCKED
# Created: 2026-04-29
# Depends on: ADR-043 (Execution Layer), ADR-044 (Operator Abstraction)
# Canonical path: /mnt/projects/cis/docs/ADRs/ADR-045.md

---

## 1. Problem

Operator routes (ADR-044) currently execute runtime scripts directly and
synchronously within the Flask request cycle. This means:

- No resumability if a job is interrupted
- No serialization enforcement at the execution layer
- No ownership record of what is running or ran
- Hardware constraint (single GPU, sequential execution) is enforced only
  by convention, not by architecture
- Operator buttons are middleware, not queue producers

The execution layer (ADR-043) defines legal state transitions.
The operator layer (ADR-044) provides human-safe controls.
Neither layer owns execution scheduling or job tracking.
That gap is the problem this ADR solves.

---

## 2. Decision

Introduce an Execution Queue Ownership Layer between the Operator
Abstraction Layer and the Execution Layer.

This layer owns:
- job intake from operator controls
- serialized single-worker execution
- job state tracking (pending → running → complete/failed)
- lock ownership during execution
- resumability on restart

This layer does NOT own:
- legal state transition rules (ADR-043)
- verification requirements (ADR-033/034/040)
- human approval gates (ADR-043)
- operator UI or button behavior (ADR-044)

## 3. execution_jobs Table Schema

```sql
CREATE TABLE IF NOT EXISTS execution_jobs (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    job_id          TEXT NOT NULL UNIQUE,
    job_type        TEXT NOT NULL,
    status          TEXT NOT NULL DEFAULT 'pending',
    payload         TEXT NOT NULL,
    result          TEXT,
    worker_id       TEXT,
    lock_acquired   TEXT,
    lock_released   TEXT,
    attempt_count   INTEGER NOT NULL DEFAULT 0,
    max_attempts    INTEGER NOT NULL DEFAULT 1,
    error           TEXT,
    created_at      TEXT NOT NULL,
    started_at      TEXT,
    completed_at    TEXT,
    updated_at      TEXT NOT NULL
);
```

**job_type values (initial):**
- `verify_contract` — L1 + optional L2 on a contract file
- `run_l2` — L2 semantic verification on a manifest + file

**status values:**
- `pending` — enqueued, not yet claimed
- `running` — claimed by worker, lock held
- `complete` — finished successfully
- `failed` — finished with error; not eligible for automatic retry
- `pending` — reset after interrupted cold start; eligible for retry
- `cancelled` — manually cancelled before execution

**Constraints:**
- Only one job may hold status `running` at any time
- This constraint is enforced at the DB level via atomic claim (see Section 5)
- Worker must acquire lock before setting status to `running`
- Lock must be released on complete, failed, or cancelled
- No job may transition from `complete` or `failed` back to `running`
- `updated_at` must be set on every status change
- Automatic retries are out of scope for this ADR. `max_attempts` is
  reserved for future use. All jobs default to `max_attempts = 1`.

**Audit semantics:**
- No rows may be deleted from `execution_jobs`
- Status fields are updated in place; this is not a violation of audit
  integrity because the full state history is preserved in
  `execution_log.md` (per ADR-043 logging requirements)
- A separate `execution_job_events` table may be introduced in a future
  ADR if row-level event history is required

## 4. Payload Requirements Per Job Type

### verify_contract
```json
{
  "file_path": "/absolute/path/to/contract.md",
  "run_l2": true
}
```
- `file_path` — required; absolute path to contract file
- `run_l2` — optional; defaults to true if Slot 1 is healthy, false otherwise
- Manifest is auto-generated by the worker from `file_path` (same logic
  as current operator route)

### run_l2
```json
{
  "file_path": "/absolute/path/to/file",
  "manifest_path": "/tmp/last_manifest.json"
}
```
- `file_path` — required
- `manifest_path` — required; must exist at job execution time

## 5. Atomic Job Claiming

The worker must claim jobs atomically to prevent race conditions
(relevant if multiple worker instances are ever introduced, and required
for correctness even with a single worker).

Claim pattern using SQLite UPDATE + rowcount check:

```python
# Atomic claim — only succeeds if job is still pending
cursor.execute("""
    UPDATE execution_jobs
    SET status = 'running',
        worker_id = ?,
        lock_acquired = ?,
        started_at = ?,
        updated_at = ?,
        attempt_count = attempt_count + 1
    WHERE job_id = ? AND status = 'pending'
""", (worker_id, ts, ts, ts, job_id))

if cursor.rowcount == 0:
    # Job was claimed by another worker or cancelled — skip
    continue
```

This enforces the single-running-job constraint at the DB level, not
by worker convention alone.

## 6. Worker Design

A single background worker thread starts with Flask and polls the
`execution_jobs` table for `pending` jobs.

Rules:
- Worker polls every 2 seconds
- Worker claims one job at a time (oldest pending first, by created_at)
- Worker uses atomic claim (Section 5) before execution
- Worker executes the job via the appropriate runtime function
- Worker writes result to `result` field as JSON
- Worker sets `status = complete` or `failed`, releases lock, sets timestamps
- `updated_at` is set on every status change

Hardware constraint enforcement:
- The single-worker design is intentional
- Only one heavy execution job runs at a time
- This is architectural, not a limitation to be worked around

## 7. Cold Start Recovery

On Flask startup, the worker scans for jobs in `running` status
left over from a previous interrupted session.

Recovery rules:
- If `job_type` is in the explicitly safe-to-retry list AND
  `attempt_count < max_attempts`: reset to `pending`,
  append note to `error` field, set `updated_at`
- Otherwise: set to `failed`, record interruption in `error` field,
  set `updated_at`

Safe-to-retry job types (initial list):
- `verify_contract` — idempotent; safe to retry
- `run_l2` — idempotent; safe to retry

Rationale: blind reset to `pending` could re-execute jobs that were
partially complete or that had side effects. Interrupted jobs default
to `failed` unless the job type is explicitly declared safe to retry.

## 8. API Routes
POST /api/queue/enqueue          — Add a job to the queue
GET  /api/queue/status           — List recent jobs and current queue state
GET  /api/queue/job/<job_id>     — Get status and result for a specific job
POST /api/queue/cancel/<job_id>  — Cancel a pending job

Operator routes (ADR-044) are refactored to enqueue jobs rather than
execute directly. They return a `job_id` immediately. The client polls
`/api/queue/job/<job_id>` for completion.

---

## 9. Operator Route Refactor

Current behavior:
`POST /api/operator/verify-contract` → executes L1 + L2 synchronously → returns result

New behavior:
`POST /api/operator/verify-contract` → enqueues job → returns `{ job_id, status: "pending" }`
Client polls `/api/queue/job/<job_id>` until `complete` or `failed`

The operator button in the dashboard must be updated to handle async
job polling rather than synchronous response.

## 10. Governance Boundary (Repeated for Build Acceptance)

Queue ownership schedules jobs. It does not define legal execution.

- ADR-043 remains the authoritative execution law
- ADR-033/034/040 remain the authoritative verification requirements
- No queue operation may bypass a verification step
- No queue operation may override a human approval gate
- Build acceptance requires confirmation that these boundaries are
  intact after implementation

---

## 11. Constraints

- Jobs may not modify their own status except through the worker
- Operator controls may not directly execute runtime scripts after
  this ADR is implemented
- No rows may be deleted from execution_jobs
- All job state changes must be logged to execution_log.md (ADR-043)

## 13. What This Does Not Solve

- Multi-step pipeline orchestration (ADR-043 scope)
- Agent-driven job generation (future ADR)
- Priority queuing (FIFO by created_at only)
- Distributed execution (hardware constraint makes this out of scope)
- Automatic retries beyond cold start recovery (future ADR)
- Row-level event history (future execution_job_events table)
