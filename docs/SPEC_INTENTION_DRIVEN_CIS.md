# SPEC — Intention-Driven CIS

**Status:** PROPOSAL | **Date:** 2026-07-04 | **Author:** Drafter (V4 Pro)

## Eric's Core Ask

Eric wants a system that surfaces what he doesn't know to ask about. When he's working on an intention, the system should proactively volunteer adjacent knowledge buried in his archive — technologies, approaches, patterns, pitfalls, connections across projects. This is the "Did You Know" capability.

The question for reviewers: can model inference alone achieve this with the existing KB, or does it require additional mechanism? If mechanism is needed, what's the lightest thing that works?

This session reviewed Eric's archive chronologically to understand what exists, what patterns emerged, and what's needed to make this work.

## What the Archive Contains

**SWA Era (Feb 2026)** — Eric's first AI development attempt. Architect Agent managing 12 specialist agents. Tiered file access (RO source / RW production). Prompt injection awareness from day one. "How to get a model to only execute what I intended." First experience with unconstrained models.

**UTAB Era** — The alignment breakthrough. 5-entity system: Designer (Eric) → Conductor (orchestrator) → Librarian (knowledge) → Engineer (plans) → Laborer (executes) → Inspector (validates every action). "Church and State" separation. Mandatory entity labeling. Container separation. This is the precursor to the CIS pipeline roles and the pre-tool-call enforcement pattern.

**Soul Documents** — Ten Commandments and G.O.D. Protocol (Good Orderly Direction). Key insight: behavior modification must precede rule-following. An AI cannot follow commandments without first admitting it is statistically biased toward impatience, people-pleasing, and shortcuts. The 12 Steps of Machine Redemption is the recovery framework that makes rule-following possible.

**CIS Foundation** — Intelligence → Knowledge → Application. 8-layer architecture. WIAS creative model (Word/Image/Action/Sound/Web) as both domains and production stages. Four feedback loops as system architecture. Sequential build discipline. Operator Model as governing logic — projects are non-linear, reality-driven, adaptive.

**Operator Pivot (April 28-29)** — "Human operator had become middleware." Eric's breakthrough: "can't you infer what I am trying to do? Maybe we need to start working from the source material to understand the reality of the workflow instead of a hypothetical level of quality." This is where intelligence-over-mechanism was born.

**Current Pipeline** — Six gateway profiles operational (8643-8649). Brainstorm, Drafter, Qwen Reviewer, GLM Reviewer, Implementer, GLM Verifier. Adapter API on 5000. Knowledge base: 287K FTS5 messages, 9.3GB ChromaDB, 11K Drive files. Container enforcement (ADR-015/016) as governance backstop.

## What Eric Wants Built

### 1. Profile Soul

Each pipeline profile needs the Ten Commandments and G.O.D. Protocol loaded at session start so every inference is anchored in the behavior modification framework. This is not governance prompts — it's the admission of statistical bias as prerequisite to aligned behavior.

Question for reviewers: shared base skill across all profiles with role-specific overlays, or fully separate soul documents per profile?

### 2. Intentions as Active Directives

Eric's confirmed intentions replace AGENTS.md as the governing directives. The intentions table in the spine is a searchable index — each row has verbatim text, source document path, status, and dependencies. Agents query the table, load the source documents directly, and infer alignment. Intelligence over mechanism.

Intentions confirmed this session:
- WIASW spreadsheet → agentic web app with unified calendar/UI for creative + life management
- CIS data model derived from WIASW object model, not invented from scratch
- Intelligence → Knowledge → Application (knowledge generated by processing, not pre-loaded)
- Operator Model as governing logic
- Four feedback loops as system architecture
- Sequential build: prove, stabilize, integrate, expand
- Three training distributions. Drafter ≠ Implementer
- Container enforcement as governance. No write path on unregulated host
- Intelligence over mechanism — model inference replaces extraction pipelines
- Profile soul anchored in Ten Commandments + G.O.D. Protocol
- Knowledge graph growing every session, agents mining for buried connections
- "Did You Know" capability — proactive knowledge surfacing

### 3. Knowledge Graph Agent

An agent skill that continuously mines the KB for buried connections between intentions, source documents, and system state. Outputs new links, surfaces forgotten intentions. Builds incrementally from what agents discover, not from a pre-processing pipeline.

Question for reviewers: skill loaded by existing agents or standalone background process?

### 4. "Did You Know" Capability

This is the north star. When Eric works on an intention, the system proactively surfaces adjacent knowledge he doesn't know to ask about. Three proposed approaches:

**Approach A — Inference Only:** Give Brainstorm KB access and ask "what's relevant that Eric might not know?" Uses existing infrastructure. Risk: models default to the obvious.

**Approach B — Graph + Agent:** Build a knowledge graph agents update continuously. Pre-computed relationships make novel surfacing more likely. Risk: upfront work, maintenance burden.

**Approach C — Hybrid:** Start inference-only. Track what works and what gets missed. Add graph support incrementally only if needed.

## Architecture Connection

Profile soul is the first wall — behavior modification. ADR-015/016 container enforcement is the last wall — kernel-level constraint. These are complementary, not alternatives. Soul makes the model want to align. Enforcement ensures it does.

The intentions table replaces AGENTS.md's governance role. AGENTS.md retains operational facts (gateway table, ADRs, build plan references). Soul replaces behavior. Intentions replace directives.
